# Security and privacy

## Identity and credentials

- No email, phone number, or conventional password is collected.
- User IDs are random UUID v4 values. Usernames are unique per server.
- Recovery keys contain 256 random bits. The server stores an Argon2 verifier and a SHA-256 lookup digest; neither is the original key. Recovery keys are returned once at account creation.
- An account recovery key restores account access only. It does not export or restore MLS identities, conversation state, or encryption keys.
- Session tokens contain 256 random bits. Only their SHA-256 digest is stored in SQLite. Sessions expire after 30 days. Recovery invalidates prior sessions, and Settings can revoke every session except the one making the request. The server closes revoked active WebSocket clients while preserving the current session.
- Windows clients store session tokens in Windows Credential Manager. A credential target is derived from the server URL, so different servers have separate credentials.
- Settings can list and revoke registered MLS device IDs, which prevents that ID from claiming unclaimed KeyPackages. Revocation does not end app sessions or account access, invalidate packages already claimed, or remove existing MLS group membership; an owner/admin must separately remove the member with an MLS Commit.
- A newly issued recovery key is kept temporarily in a separate Credential Manager entry until the user confirms saving a backup. The client removes that temporary copy when the user continues.

## Message data

In the 4.0 client, an authenticated MLS commit that changes a previously verified direct-peer identity or group membership code pauses processing later crypto events. Settings in the conversation then require the user to compare the previous and current codes through a trusted channel and explicitly approve the change before processing resumes. The client stores incoming MLS event cursors in the same SQLite transaction as the MLS state and decrypted local message cache to avoid replaying an already-applied message after a restart; the prior client cursor is imported on first upgrade. An automated two-account test now covers direct Welcome, message encryption/decryption, persistent state across SQLite reopen, and replay rejection. Real two-device Windows, multi-device, and adversarial review are still required.

Messages in chats without encryption enabled are stored as normal text in SQLite. Direct chats and group text can opt in to experimental MLS encryption after members prepare devices and compare identity codes through a trusted separate channel. Starting setup locks the conversation on the server, which requires the `e2e1:` envelope for both direct and group messages; API validation and a SQLite trigger close the race between that lock and a concurrent plaintext insert. The server does not inspect or validate opaque MLS payloads, so a modified client can still submit arbitrary bytes under that envelope. With the unmodified app, messages sent after setup are encrypted on the sender's device and decrypted on the recipient's device; the server stores ciphertext and still sees conversation, sender, and timing metadata. Targeted MLS setup events also reveal their recipient to the server. Earlier messages remain plaintext. Search checks the 50 newest messages per conversation locally and does not send the search phrase to the server; older messages are not included in this local search yet. Encrypted group invite-code joins remain blocked. Owners and admins can add accepted friends using a staged MLS Commit and targeted Welcome; they can also remove non-owner members with a staged MLS Commit sent to remaining members. A non-owner can submit an authenticated MLS self-Remove proposal, which only the unique owner can commit; the departing client remains in the group until the commit is confirmed, then deletes local group state. The client verifies new KeyPackages, checks resulting rosters, and requires re-checking the full group code after membership changes. The server relays opaque MLS payloads and cannot independently prove that a submitted Commit matches the roster change: commit contents are validated only by the receiving clients, which reject mismatched rosters and never accept a commit that adds a leaf for an account the server recorded as deleted (such a leaf may only stay or be removed). For a removal the server records the target account with the operation and refuses a request whose declared target differs from the route's target. These paths remain experimental. Automated multi-account tests cover these membership flows; they still need real multi-device interoperability and security review. Newly uploaded files in an encrypted chat are encrypted on Windows in 1 MiB AES-256-GCM chunks; the key, filename, media type, and chunk manifest are carried only inside an MLS-encrypted message. The server stores the encrypted bytes with generic metadata and still sees the uploader, conversation, timing, and byte count. Previously uploaded attachments remain plaintext. The local MLS state is encrypted with AES-256-GCM; its key is kept in Windows Credential Manager. Losing that Windows credential also loses access to this device's MLS state. The account recovery key does not restore it, and GhostChat currently has no encrypted MLS-state export/import flow. This implementation has not had protocol interoperability or independent security review and is not ready for a production security claim. Backups are not encrypted by GhostChat.

The desktop's built-in server binds to loopback; the standalone server binds `0.0.0.0:38241` by default. Remote deployments should terminate TLS at a maintained reverse proxy, keep the app server private behind a firewall, and restrict access to the SQLite file and its backups. The sample environment file contains placeholders only.

## Abuse controls and limitations

Account creation, recovery, friend requests, message sends, voice signaling, blocking changes, and reports have process-local rate limits. These counters reset when the server restarts and do not coordinate across multiple server replicas; an optional Redis-backed limit (see [DEPLOYMENT.md](DEPLOYMENT.md#environment)) adds a shared request limit. The app server does not implement a proxy-aware IP limiter, bundle or operate a TURN service, moderator roles, or a moderation console/review workflow. User reports store the reporter, target, optional direct-conversation reference, selected category, and only the details the reporter typed; no messages or attachments are copied into a report automatically. Reports are stored in the server's SQLite database and included in the reporter's account export. Blocking removes the friendship and pending requests, hides the pair from search, and denies new direct messages, direct file uploads, and one-to-one WebRTC signaling; it does not erase prior history or alter shared group chats. Unblocking does not restore a friendship. Voice signaling is transient but includes ICE candidates and call metadata. Calls never connect peer-to-peer: address protection is always on, so media goes through TURN, LiveKit or the GhostChat server relay, and callers do not learn each other's network addresses. The relay still observes client network addresses and traffic volume; media is encrypted in transit to the relay, which can access it.

When TURN or LiveKit is not configured or cannot be reached (for example behind an HTTP-only Cloudflare tunnel), direct and group call audio and screen sharing are relayed through the GhostChat server itself over an authenticated WebSocket (`/v1/media/ws`). Like TURN and LiveKit, **this relayed media passes through the GhostChat server and is not end-to-end encrypted**: the server operator, and a tunnel provider that terminates TLS, can access the media in transit. The server does not store it. Peers still do not learn each other's network addresses. Joining needs a valid session and the same rights as call signaling (the two members of a direct conversation that do not block each other; current members of a group); a block or group removal stops forwarding to and from that user immediately. Frame size and rate are limited per connection, and limits are process-local.

When LiveKit is configured, group voice and screen sharing are relayed through the server operator's LiveKit SFU. Media is encrypted in transit to the SFU, but the SFU terminates that transport and can access media; this is not end-to-end encryption. LiveKit also handles participant identity, room, and network metadata. GhostChat checks group membership when issuing a short-lived join token and asks LiveKit to disconnect all active sessions for an account after it leaves or is removed from a group. If this management request fails, the normal-client membership update still asks the desktop to leave. Self-hosted LiveKit does not revoke an already-issued participant token, so a removed participant may reconnect using a still-valid token until its expiry; Cloud token revocation behavior differs. The self-hosted reconnect behavior still needs real-server validation.

The WebSocket accepts an initial token frame rather than putting credentials in the URL. CORS permits the Tauri desktop origin and the local development origin. Every protected HTTP action checks the session and relevant conversation/friend authorization. The app has no telemetry or paid API dependency. Windows desktop notifications are delivered while the app is running and may show titles on the Windows lock screen; disable them in GhostChat or Windows settings on shared devices. GhostChat does not provide push notifications after the desktop app exits.

## Data lifecycle

- Export: Settings downloads account profile, friends, conversations, stored message history, and any opaque crypto-relay events as JSON.
- Delete: account deletion removes that account, sessions, friend relationships, its conversations, and those messages from the active database. Copies in operator backups are not removed automatically.
- Backup: stop the server cleanly, then copy the SQLite database and protect the copy as sensitive data. Do not copy a live WAL database without using a SQLite-aware backup procedure.

This project has not had an independent security review or penetration test. Chats are not end-to-end encrypted unless encryption is enabled for them; the optional direct/group MLS encryption is experimental and has the limits listed above. Calls and screen sharing are never end-to-end encrypted.
