### Release notes callout

The desktop MLS lookup-key migration (A-19, was T3-1) is **not downgrade-safe**. On first crypto use the new build rewrites existing KeyPackage and proposal rows in the local MLS storage (`HashReference` moves from a one-way digest to deterministic AEAD, `GCK\x02`). An older desktop build cannot read the migrated storage. Do not let users roll back to a build from before this change.

### Owner decisions

- A-7: account deletion removes only the user's membership. Ownership passes to the admin, else the member, with the lowest `conversation_members` rowid (join order for later joiners; effectively arbitrary among the founding members, who are inserted sorted by user id). A group is deleted only when it becomes empty. Direct conversations are still deleted with the account.
- A-7 (note): account deletion also removes the deleted user's planner polls and events in surviving groups, including other members' votes and RSVPs on them.
- A-8: blocking also forbids editing old direct messages (403, like sending).
- A-9: kept as is. A removed or departed member can still delete their own old messages (sender privacy).
- A-61 (T6-9): a failed send restores the typed draft when the composer is still empty and the user is on the same chat. It is not restored when encrypted ciphertext is queued for automatic retry (that would double-send).
- A-7b: tolerate leaves of deleted accounts in encrypted groups and let an owner/admin client remove them. Implemented as a server record per locked group plus an owner-client removal commit (only the owner's client triggers it automatically, so two admins never race commits for the same epoch; the server accepts owner or admin).
- A-69: decode pending encrypted messages before applying membership changes. `max_past_epochs` stays 0.
- A-62 (T6-10): a failed startup update check shows the "Could not check for updates" warning and boots. A found update stays mandatory.

### Needs Windows verification

- A-7b: Three Windows accounts (two PCs is enough if C uses a third account on one of them), encrypted group A (owner)/B/C. C deletes her account. Confirm B still decrypts A's next message, A's client publishes the removal commit by itself (on opening the group or the next relay sync), both see the new group code, and messages still decrypt afterwards. Separately: an unfinished lock started by C still cannot be completed (not fixed).
- A-69: Two Windows PCs, encrypted group. Bob keeps another chat open while Alice sends 3 messages and then adds or removes a member. Bob opens the group: all 3 messages decrypt. Repeat with Bob's app closed, then started.
- A-21 (T3-3): Encrypted DM between two Windows accounts. Alice sends text, Bob opens the chat (history and live delivery); every message decrypts instead of "could not be decrypted on this device".
- A-22 (T3-4): Real Credential Manager. Sign in, lock the workstation / switch the logon session while the app is open and run an encrypted action. Confirm the stored key is not replaced and the encrypted history still opens after restart.
- A-23 (T3-5): Log out and receive `session_revoked` on Windows. Confirm the token entry is really gone from Credential Manager (check with `cmdkey /list`).
- A-35 (T4-2): Two Windows PCs: A calls B, B's network drops 10 s, call recovers without hanging up; with the network down for over 30 s before connecting, the call ends instead of hanging in "connecting".
- A-48 (T5-9): Two Windows PCs: both click Call at the same instant. Exactly one call is established and neither side is left with an unanswered incoming offer.
- A-51 (T5-12): Direct call and group screen share: stop sharing via the Windows "Stop sharing" bar and by closing the shared window. The share indicator clears on both sides.
- A-52 (T5-13): Mid-call, unplug the USB microphone, then plug in another and select it. Direct: call mutes with a reason. Group: audio resumes on the new device.
- A-55 (T6-3): Encrypted chat A with a pending lock request that fails; switch to chat B. B's header keeps its own "Encrypted" state and error text.
- A-56 (T6-4): Open an encrypted chat with about 50 messages and switch to another chat while it decodes. The second timeline never shows messages from the first.
- A-26 (T3-8): Configure the desktop with a server under a path prefix (for example a reverse proxy at `https://host/chat/`). Send an encrypted attachment in a locked chat and open it on the other PC. Record whether upload and download hit `https://host/v1/...` (proxy log) instead of `https://host/chat/v1/...`; with the current code they do, so the transfer fails.
- A-31 (T3-13): Two Windows PCs, locked chat. Send a multi-chunk encrypted attachment (larger than one chunk) and download it on the other PC: the file matches byte for byte (compare hashes). Then, with a debugging proxy, swap two chunks, truncate the last one, and append bytes: each download fails with an error and leaves no partial file.
